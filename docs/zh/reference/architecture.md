# 实现方式

Vflash 使用 PyTorch 和 Triton 原生实现 H3 推理。它直接管理去噪执行过程，加载已编译的数据，不依赖 LightX2V 的运行时或模型对象结构。

## 当前数据流 {#data-path}

```text
编译权重 + 调度数据 + 辅助张量
                ↓
条件包 → Vflash 会话 → 视频和音频 latents
```

条件包提供已编码的请求信息和初始视频、音频状态。会话执行 H3 的多模态 Transformer，并按照所选调度方式更新两组 latent 张量。

提示词和参考素材编码发生在这条路径之前；latent 解码和媒体文件生成发生在之后。这些前后处理目前还不包含在公开运行时中。

## 两种内存策略 {#memory-strategies}

对于 **48 GB 版 4090**，编译权重常驻显存。多个请求可以复用已经加载的模型，避免重复加载。

对于 **20 GB 版 3080**，权重保存在锁页系统内存中，通过少量 GPU 缓冲区轮流加载。传输与计算可以重叠；只有 GPU 完成上一次读取后，缓冲区才能装入下一块权重。这样可以减少显存需求，但会增加系统内存占用和传输工作。

两种执行方式使用同一个会话接口，但不意味着跨 GPU 架构的性能或张量结果完全相同。

## 双 GPU 协作 {#parallel}

双卡会话持有一个进程、两个 CUDA 上下文、两个有事件保护的显存缓冲环，以及一个局部 NCCL 通信组。两个 CPU 线程分别提交 CUDA 工作，不建立全局 `torch.distributed` 状态，也不创建第三方框架模型结构。

权重张量并行将列投影及其 LoRA up 矩阵分片，再将行投影及其 LoRA down 矩阵分片。行并行的低秩局部结果先归约，再执行复制到两卡的 up 投影。序列/注意力头并行则先划分 token 行，通过 Q/K/V 交换让每张卡获得部分头的完整序列，再将注意力输出发回原来的 token 所有者。奇数序列只在传输时补齐；补齐位置的 key 和 value 不参与 softmax。

序列/头并行共享一份锁页主机权重，权重 TP 保存紧凑分片而非两份完整主机副本。两种策略每张卡都使用两个显存槽，并复用已有传输事件。序列/头并行把注意力头分成四组以重叠通信和计算。会话关闭时释放 NCCL；任一 rank 失败后会中止另一个 rank，并禁止复用该会话。

## LoRA 执行 {#lora-execution}

编译资源包含指定 LoRA 和调度数据。当前配置保留基础权重之外的低秩残差计算，并使用精确注意力。切换 LoRA 需要更换资源，不能在每次请求中随意切换。

Vflash 可以使用兼容的 LightX2V Turbo 权重，无需导入 LightX2V 推理框架。模型兼容性与推理代码实现是两件独立的事。

## 会话与服务 {#sessions}

命令行一次调用创建一个会话。HTTP 服务启动一个 CUDA worker 进程，在首个任务中加载固定配置，后续任务在该进程中串行执行。

worker 持有权重和 CUDA 状态，进程退出时释放设备上下文。HTTP 进程负责请求检查、任务状态和结果下载，不直接执行模型计算。

服务的任务记录保存在内存中。接入它的应用需要自行提供持久任务记录、用户身份、资源调度和用量管理。实际运行行为见 [Docker 与 API](../guide/docker)。
